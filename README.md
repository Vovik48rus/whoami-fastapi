# whoami-fastapi

FastAPI-аналог [traefik/whoami](https://github.com/traefik/whoami), подготовленный
как артефакт для практической/лабораторной работы по развёртыванию за
реверс-прокси Apache/Nginx с балансировкой нагрузки (L4/L7), DNS-балансировкой,
TLS/SSL-терминацией и асинхронной обработкой запросов.

## Что внутри

```
whoami-fastapi/
├── app/
│   ├── main.py          # FastAPI-приложение и все эндпоинты
│   ├── config.py         # конфигурация через переменные окружения
│   └── redis_client.py   # клиент внешнего хранилища (Redis) с обработкой ошибок
├── requirements.txt
├── Dockerfile
├── docker-compose.yml    # 2 ноды приложения + Redis + Nginx-балансировщик
├── nginx.conf            # пример L7-балансировки (round-robin)
└── .env.example
```

## Эндпоинты

| Метод | Путь            | Описание |
|-------|-----------------|----------|
| GET   | `/`             | Текстовый вывод в стиле оригинального `whoami`: hostname, IP, заголовки запроса |
| GET   | `/ui`           | Та же информация в HTML |
| GET   | `/api`          | JSON-версия с полным описанием ноды и запроса |
| GET   | `/health`       | Liveness-проверка (не зависит от Redis) |
| GET   | `/health/ready` | Readiness-проверка (200, если доступен Redis, иначе 503) |
| GET   | `/visits`       | Глобальный счётчик запросов, общий для всех нод (Redis `INCR`) |
| GET   | `/visits/recent`| Последние запросы из общего лога (Redis `LIST`) |
| GET   | `/session`      | Счётчик визитов текущей сессии (cookie + Redis, TTL) |
| GET   | `/delay?ms=200` | Имитация асинхронного I/O-ожидания (`asyncio.sleep`) |
| GET   | `/bench`        | Максимально лёгкий эндпоинт для нагрузочного тестирования |
| GET   | `/version`      | Версия приложения, Python, платформа |

Каждый ответ дополнительно содержит заголовки `X-Node-Name`, `X-Node-Hostname`,
`X-Node-Pid` — удобно смотреть балансировку через `curl -i` или devtools.

## Как это соответствует ограничениям задания

**1. Определение ноды, ответившей на запрос.**
`/`, `/ui`, `/api` и HTTP-заголовки `X-Node-*` однозначно показывают hostname
контейнера, `NODE_NAME` из окружения, ID контейнера (если приложение
запущено в Docker) и PID процесса.

**2. Отказоустойчивое хранилище.**
Все данные, которые нужно сохранять между запросами (глобальный счётчик,
лог запросов, счётчики сессий), лежат **не в памяти процесса и не в файле
на диске ноды**, а во внешнем Redis, вынесенном в отдельный контейнер/сервис.
Если падает одна из нод FastAPI — остальные ноды продолжают отдавать те же
данные, потому что состояние не привязано к конкретному backend'у. Это
проверено вручную (см. раздел «Проверка отказоустойчивости» ниже).
Если недоступен сам Redis — эндпоинты, зависящие от хранилища (`/visits`,
`/session`), отвечают `503` с понятным сообщением, а не роняют всё
приложение: `/`, `/api`, `/health` продолжают работать.
Для продакшн-уровня отказоустойчивости самого Redis (а не только нод
приложения) в реальном развёртывании стоит использовать Redis Sentinel
или Redis Cluster — здесь для простоты лабораторной используется один
инстанс Redis с AOF-персистентностью.

**3. Приложение не терминирует TLS.**
`uvicorn` запускается без `--ssl-keyfile`/`--ssl-certfile`, слушает только
plain HTTP (см. `Dockerfile` и `docker-compose.yml`). Сертификаты и
HTTPS-листенер добавляются позже на уровне Nginx/Apache перед этим
контейнером — `nginx.conf` в проекте содержит только `listen 80` и
комментарий о том, куда добавить `listen 443 ssl`.

**4. Сессии не в памяти и не в локальных файлах.**
`/session` идентифицирует клиента через cookie со случайным UUID, а сами
данные сессии (счётчик визитов, TTL) хранятся только в Redis
(`INCR` + `EXPIRE` в одном pipeline). При выходе из строя ноды, создавшей
сессию, любая другая нода за балансировщиком продолжает работу с той же
сессией — sticky sessions не требуются.

## Локальный запуск (без Docker)

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# отдельно поднять Redis, например:
docker run --rm -p 6379:6379 redis:7-alpine

NODE_NAME=local-dev REDIS_HOST=localhost uvicorn app.main:app --reload
```

## Запуск демо-стенда (2 ноды + Redis + Nginx)

```bash
docker compose up --build
```

- Балансировщик слушает `http://localhost:8080`
- Обновите страницу/curl несколько раз — в `X-Node-Name` будет чередоваться
  `node-1` / `node-2` (round-robin из `nginx.conf`)
- `curl http://localhost:8080/visits` — счётчик общий независимо от того,
  какая нода ответила

### Проверка отказоустойчивости

```bash
# счётчик увеличивается через балансировщик
curl -s http://localhost:8080/visits

# «роняем» одну ноду
docker compose stop app1

# балансировщик продолжает отвечать через app2, счётчик не сбросился
curl -s http://localhost:8080/visits

# поднимаем ноду обратно
docker compose start app1
```

Ручная проверка этого сценария (без Docker, напрямую по портам двух
инстансов uvicorn с общим Redis) была выполнена при подготовке проекта:
общий счётчик и счётчик сессии продолжали расти на второй ноде после
остановки первой, без потери накопленных значений.

## Дальнейшие шаги для лабораторной работы №3

- Заменить `nginx.conf` на конфигурацию с `listen 443 ssl` и сертификатами
  (Let's Encrypt / самоподписанные) — приложение менять не требуется.
- Для демонстрации L4-балансировки можно использовать `stream {}`-блок
  Nginx или `mod_proxy_balancer` Apache — приложение одинаково работает
  в обоих случаях, так как ничего не знает о транспортном уровне.
- Для DNS-балансировки — добавить несколько A-записей, указывающих на
  разные инстансы Nginx/приложения, либо использовать round-robin DNS
  перед балансировщиком.
- Масштабировать количество нод: `docker compose up --scale app1=1 --scale app2=1`
  либо добавить в `docker-compose.yml` ещё сервисы `app3`, `app4` и
  прописать их в `upstream` в `nginx.conf`.
